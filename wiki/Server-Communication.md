# ارتباط با سرور — پل بین خودرو و بک‌اند

هر چیزی که باید از خودرو به سرور برسد (یا برعکس)، از یک نقطهٔ واحد رد می‌شود: **Server Management**. هیچ بخش دیگری از Firmware اجازه ندارد مستقیم با سرور صحبت کند.

## چطور کار می‌کند

```
بخش‌های دیگر (GPS, Diagnostic, Hardware Input, ...)
      ↓
Telemetry / Event / Request
      ↓
Server Management
      ↓
EC200U Manager (ماژول سیم‌کارتی)
      ↓
شبکهٔ سلولار
      ↓
سرور بک‌اند
```

نکتهٔ مهم: هیچ بخشی برای فرستادن یک پیام، منتظر جواب سرور نمی‌ماند. درخواست را تحویل می‌دهد و به کار خودش ادامه می‌دهد؛ Server Management در پس‌زمینه، مرحله‌به‌مرحله (در هر دور از حلقهٔ اصلی برنامه، یک قدم کوچک) کار ارسال را جلو می‌برد.

اگر فرمانی از سرور بیاید (مثلاً «موتور را قطع کن»)، این بخش هرگز خودش آن را اجرا نمی‌کند — فقط اعتبارسنجی اولیه می‌کند و آن را به بخش صاحب آن قابلیت (مثلاً [[Outputs]]) تحویل می‌دهد.

## نکات جالب

* **دو صف کاملاً جدا:** یکی برای رویدادهای مهم (Event، مثل «ضربه خورد») و یکی برای داده‌های معمولی و پیوسته (Telemetry، مثل موقعیت GPS هر چند ثانیه). این‌ها قصداً در دو خط جدا حرکت می‌کنند تا یک سیل داده‌های معمولی، هرگز یک هشدار مهم را عقب نیندازد.
* **قطع اینترنت خودرو را فلج نمی‌کند.** اگر سرور در دسترس نباشد، بقیهٔ بخش‌های TCU (GPS، قفل درب، پیامک، ...) کاملاً مستقل به کارشان ادامه می‌دهند؛ فقط داده‌ای که باید فرستاده شود، در صف می‌ماند تا ارتباط برقرار شود.
* وضعیت اتصال هم مثل خیلی چیزهای دیگر در این پروژه، سه‌حالته و ساده است: `DISCONNECTED`، `CONNECTING`، `CONNECTED` — دقیقاً همان چیزی که روی گوشی موبایل هم می‌بینید.
* این بخش حتی «نوع سرویس» (HTTP یا MQTT یا هرچه باشد) را نمی‌شناسد — همهٔ آن جزئیات پشت همان مرز واحد با ماژول سیم‌کارت (EC200U Manager) مخفی است، دقیقاً به همان فلسفهٔ صفحهٔ [[Hardware-Proxy]].
