پیوست فنی شماره ۳
معماری مدیریت داده و الگوی Provider / Latest Value
۱. هدف
این پیوست، الگوی معماری مورد استفاده برای تأمین، به‌روزرسانی و مصرف داده‌هایی را مشخص می‌کند که تهیه‌ی آن‌ها ممکن است زمان‌بر باشد.
هدف اصلی، جلوگیری از وابستگی مصرف‌کنندگان به فرآیندهای زمان‌بر و حفظ ویژگی Non-Blocking در معماری Firmware است.
اصل محوری این معماری عبارت است از:
مصرف‌کننده نباید مسئول تأمین داده‌ی زمان‌بر باشد.
در صورتی که تأمین یک داده بتواند باعث انتظار، توقف یا تأخیر محسوس در مسیر اجرای Firmware شود، فرآیند تأمین داده از مصرف آن جدا می‌شود.
________________________________________
۲. اصل تفکیک Acquisition و Consumption
در معماری Firmware دو فعالیت از یکدیگر تفکیک می‌شوند:
Data Acquisition
فرآیند دریافت، اندازه‌گیری، محاسبه یا استخراج داده.
ممکن است شامل عملیات‌هایی مانند:
•	دریافت موقعیت GNSS
•	اندازه‌گیری ولتاژ یا جریان
•	دریافت وضعیت یک سخت‌افزار
•	پردازش داده‌ی دریافتی از یک Peripheral
•	دریافت اطلاعات از EC200U
•	انجام محاسباتی که نیازمند چند مرحله اجرای Super Loop هستند
باشد.
Data Consumption
استفاده از داده‌ی آماده توسط سایر بخش‌های سیستم.
مصرف‌کننده نباید برای دریافت داده وارد فرآیند Acquisition شود.
مدل معماری:
Data Source
     │
     ▼
Data Acquisition
     │
     ▼
Latest Value
     │
     ├──────────► Consumer A
     ├──────────► Consumer B
     └──────────► Consumer C
بنابراین زمان‌بر بودن Acquisition نباید به مصرف‌کننده منتقل شود.
________________________________________
۳. معیار تصمیم‌گیری برای استفاده از Provider
برای هر عملیات ابتدا باید مشخص شود که آیا انجام آن در محل مصرف قابل قبول است یا خیر.
عملیات سریع
اگر کل عملیات به‌صورت مستقل و سریع قابل انجام باشد و باعث انتظار یا توقف Super Loop نشود، می‌تواند در همان Management یا Service انجام شود.
Consumer
   │
   ▼
Fast Operation
   │
   ▼
Result
در این حالت ایجاد Provider مستقل الزامی نیست.
عملیات زمان‌بر
اگر انجام عملیات نیازمند زمان، انتظار، چند مرحله پردازش یا تعامل غیرهمزمان با سخت‌افزار باشد، Acquisition باید از Consumer جدا شود.
Consumer
   │
   ▼
Latest Value
و در سمت دیگر:
Provider
   │
   ├── Acquisition
   ├── Processing
   └── Update Latest Value
معیار معماری، رفتار Non-Blocking است و نه یک عدد زمانی ثابت.
عددهایی مانند ۵۰۰ میلی‌ثانیه می‌توانند در تحلیل یک عملیات به‌عنوان معیار تجربی مورد استفاده قرار گیرند، اما در این معماری یک سقف زمانی عمومی و اجباری برای تمام Managementها تعریف نمی‌شود.
________________________________________
۴. Data Provider
برای داده‌هایی که Acquisition آن‌ها زمان‌بر است، یک Data Provider مسئول تأمین و به‌روزرسانی داده خواهد بود.
Provider دارای مسئولیت‌های زیر است:
1.	اجرای فرآیند Acquisition
2.	مدیریت مراحل لازم برای تهیه‌ی داده
3.	جلوگیری از Blocking
4.	تصمیم‌گیری درباره زمان مناسب به‌روزرسانی
5.	ثبت آخرین داده‌ی به‌دست‌آمده
6.	ثبت Timestamp داده
7.	فراهم کردن داده برای مصرف‌کنندگان
Provider خود در Super Loop فرصت اجرا دریافت می‌کند.
                 SUPER LOOP
                     │
                     ▼
              Provider_Process()
                     │
          ┌──────────┴──────────┐
          │                     │
       No Work              Acquisition
          │                     │
        Return                  ▼
                            Update Data
                                │
                                ▼
                           Latest Value
Super Loop مسئول تصمیم‌گیری درباره‌ی زمان Acquisition نیست.
Super Loop فقط فرصت اجرای Provider را فراهم می‌کند.
________________________________________
۵. Policy داخلی Provider
هر Provider مسئول Policy مربوط به خودش است.
این Policy می‌تواند تعیین کند:
•	چه زمانی داده به‌روزرسانی شود؛
•	با چه تناوبی Acquisition انجام شود؛
•	در چه شرایطی Acquisition انجام شود؛
•	در چه شرایطی Acquisition متوقف یا کند شود؛
•	در صورت عدم موفقیت چه رفتاری داشته باشد؛
•	در Power Modeهای مختلف چه سطحی از فعالیت انجام شود.
بنابراین Super Loop نباید شامل چنین سیاست‌هایی باشد:
اگر GPS است هر ۱۰ ثانیه اجرا کن
اگر Battery است هر ۱ ثانیه اجرا کن
...
این سیاست‌ها متعلق به Provider هستند.
مدل صحیح:
Super Loop
    │
    ├── GPS Provider
    │       └── خودش می‌داند چه زمانی Update کند
    │
    ├── Battery Provider
    │       └── خودش می‌داند چه زمانی Measure کند
    │
    └── Signal Provider
            └── خودش می‌داند چه زمانی Update کند
________________________________________
۶. Latest Value
Provider آخرین داده‌ی قابل استفاده را نگهداری می‌کند.
این داده برای مصرف‌کنندگان یک منبع عمومی است.
هر بخش سیستم که به داده نیاز داشته باشد، آن را مستقیماً می‌خواند.
نمونه:
value = Battery_GetLatest();
یا:
position = GPS_GetLatest();
این API نباید Acquisition جدیدی را آغاز کند.
به عبارت دیگر:
GetLatest()
    ≠
AcquireNewData()
GetLatest() یک عملیات سریع و قابل پیش‌بینی برای خواندن داده‌ی موجود است.
________________________________________
۷. مالکیت داده
Provider مالک فرآیند تأمین و به‌روزرسانی داده است.
اما داده‌ی حاصل، مالک اختصاصی ندارد و می‌تواند توسط چند مصرف‌کننده مورد استفاده قرار گیرد.
              Battery Provider
                     │
                     ▼
              Latest Battery
                     │
          ┌──────────┼──────────┐
          ▼          ▼          ▼
        Power      Server     Health
در نتیجه برای استفاده از یک داده، نیازی به ایجاد زنجیره‌ی وابستگی بین مصرف‌کنندگان وجود ندارد.
هر Consumer مستقیماً به Contract داده دسترسی دارد.
________________________________________
۸. Timestamp
هر Latest Value در صورت نیاز باید همراه با Timestamp مربوط به زمان تولید یا دریافت داده نگهداری شود.
نمونه مفهومی:
GPS Data
├── Latitude
├── Longitude
└── Timestamp
یا:
Battery Data
├── Voltage
└── Timestamp
بنابراین Consumer می‌تواند علاوه بر مقدار داده، زمان مربوط به آن را نیز در اختیار داشته باشد.
این موضوع امکان تصمیم‌گیری درباره‌ی تازگی داده را بدون وابستگی به فرآیند Acquisition فراهم می‌کند.
________________________________________
۹. داده‌ی قدیمی و تازگی داده
معماری Latest Value به معنی تضمین «لحظه‌ای بودن» داده نیست.
Latest Value یعنی:
آخرین داده‌ای که Provider موفق به تأمین و ثبت آن شده است.
بنابراین ممکن است داده‌ای که Consumer دریافت می‌کند مربوط به گذشته باشد.
وجود Timestamp این موضوع را آشکار می‌کند.
برای مثال:
Latest GPS
Value:  ...
Timestamp: T-30s
Consumer در صورت نیاز می‌تواند بر اساس Timestamp درباره‌ی قابل‌استفاده بودن داده تصمیم بگیرد.
در این مرحله، تعریف یک مدل عمومی و اجباری برای Validity یا Quality برای تمام داده‌ها الزامی نیست.
در صورتی که نوع خاصی از داده نیازمند مفهوم اعتبار یا کیفیت باشد، این اطلاعات می‌تواند در Contract همان داده تعریف شود.
________________________________________
۱۰. Provider و Power Mode
Providerها باید نسبت به Power Mode سیستم آگاه باشند.
این به معنی کنترل Provider توسط Power Manager نیست.
Power Manager فقط Mode سیستم را تعیین می‌کند:
NORMAL
LOW_POWER
هر Provider رفتار مناسب خود را در هر Mode تعیین می‌کند.
برای مثال:
NORMAL
  └── GPS Acquisition با نرخ بالاتر

LOW_POWER
  └── GPS Acquisition با نرخ پایین‌تر
بنابراین:
Power Manager تعیین‌کننده‌ی Mode است؛ Provider تعیین‌کننده‌ی نحوه‌ی فعالیت خودش در آن Mode است.
این اصل از ایجاد یک Power FSM مرکزی برای کنترل جزئیات همه‌ی Providerها جلوگیری می‌کند.
________________________________________
۱۱. Provider و Super Loop
Provider یک عضو مستقل در چرخه‌ی اجرای Super Loop است.
نمونه:
while (1)
{
    PowerManagement_Process();

    GPSProvider_Process();

    BatteryProvider_Process();

    ServerManagement_Process();

    DiagnosticManagement_Process();

    SMSManagement_Process();
}
هر Provider:
•	وضعیت داخلی خود را نگهداری می‌کند؛
•	زمان مناسب Acquisition را تشخیص می‌دهد؛
•	در صورت نیاز یک بخش کوچک از فرآیند را اجرا می‌کند؛
•	در صورت نیاز Latest Value را به‌روزرسانی می‌کند؛
•	و سریع به Super Loop بازمی‌گردد.
هیچ Provider مجاز به ایجاد حلقه‌ی انتظار، Delay یا Blocking نیست.
________________________________________
۱۲. Provider در برابر Management
Provider و Management از نظر مسئولیت یکسان نیستند.
Management
مسئول مدیریت یک قابلیت یا فرآیند است.
مثلاً:
•	Server Management
•	SMS Management
•	Diagnostic Management
•	GPS Management
Provider
مسئول آماده نگه‌داشتن یک داده برای مصرف سایر بخش‌ها است.
ممکن است یک Provider خودش به‌صورت مستقل وجود داشته باشد یا بخشی از یک Management باشد.
معیار اصلی، مسئولیت معماری است و نه الزاماً نام Module یا فایل.
بنابراین در این مرحله معماری الزام نمی‌کند که برای هر داده حتماً یک Module مستقل ایجاد شود.
________________________________________
۱۳. Provider در برابر Request / Queue
Data Provider برای داده است.
Request و Queue برای عملیات هستند.
Data
Provider
   ↓
Latest Value
   ↓
Consumer
Operation
Request
   ↓
Queue
   ↓
Management
   ↓
Execution
مثلاً:
Battery Voltage
    ↓
Latest Value
ولی:
Send SMS
    ↓
Request
    ↓
SMS Queue
    ↓
SMS Management
مصرف‌کننده نباید یک داده را به‌صورت Request سفارش دهد، اگر آن داده باید به‌صورت مستمر آماده باشد.

۱۴. مثال: GPS
GPS نمونه‌ی واضحی از داده‌ای است که Acquisition آن می‌تواند زمان‌بر باشد.
مدل صحیح:
GNSS Source
     ↓
GPS Provider
     ↓
Acquire / Process
     ↓
Latest Position
     │
     ├──► Server
     ├──► Event Detection
     └──► سایر مصرف‌کنندگان
وقتی Server به موقعیت نیاز دارد، نباید Acquisition جدیدی را آغاز کند.
بلکه:
Server
   ↓
GPS_GetLatest()
   ↓
Position + Timestamp
فرآیند دریافت موقعیت مستقل از نیاز لحظه‌ای Server ادامه دارد.
________________________________________
۱۵. مثال: Battery Measurement
اگر اندازه‌گیری باتری زمان‌بر باشد:
Battery Provider
      ↓
Measure
      ↓
Filter / Process
      ↓
Latest Battery Value
      ↓
     ┌───────┬────────┬────────┐
     ▼       ▼        ▼
   Power   Server   Health
هر مصرف‌کننده بدون انجام Measurement جدید، مقدار آماده را دریافت می‌کند.
________________________________________
۱۶. مثال: داده‌ای که سریع است
اگر یک وضعیت سخت‌افزاری بدون انتظار قابل خواندن باشد، ایجاد Provider مستقل ضروری نیست.
مثلاً:
GPIO_Read(ACC)
اگر این عملیات سریع و غیرمسدودکننده باشد، می‌تواند مستقیماً در Management مربوطه انجام شود.
بنابراین معماری از ایجاد لایه‌های غیرضروری جلوگیری می‌کند.
________________________________________
۱۷. اصل عدم وابستگی Consumer به Acquisition
یکی از مهم‌ترین قواعد این معماری:
Consumer نباید بداند داده چگونه، کِی و با چه فرآیندی تأمین شده است.
Consumer فقط Contract داده را می‌شناسد.
برای مثال:
GPS_GetLatest()
نباید Consumer را مجبور کند که بداند:
•	GNSS فعال است یا خیر؛
•	چند Fix گرفته شده؛
•	چند بار Retry شده؛
•	EC200U چه دستوری دریافت کرده؛
•	Acquisition در چه مرحله‌ای قرار دارد.
تمام این جزئیات متعلق به Provider و لایه‌های پایین‌تر است.
________________________________________
۱۸. رابطه با EC200U Manager
این اصل با مرزبندی EC200U نیز سازگار است.
              GPS Consumer
                    │
                    ▼
              GPS Provider
                    │
                    ▼
             EC200U Manager
                    │
                    ▼
                  EC200U
Consumer نباید مستقیماً با فرآیند زمان‌بر GNSS در EC200U درگیر شود.
EC200U Manager جزئیات مربوط به:
•	AT Command
•	GNSS acquisition
•	timeout
•	retry
•	recovery
•	modem state
را مدیریت می‌کند.
GPS Provider نتیجه‌ی مورد نیاز Firmware را دریافت کرده و Latest Value را آماده نگه می‌دارد.
________________________________________
۱۹. رابطه با Event
یک داده‌ی Maintained می‌تواند علاوه بر مصرف مستقیم، مبنای Detection یک Event نیز قرار گیرد.
برای مثال:
Battery Provider
      ↓
Latest Battery Voltage
      │
      ├──────────► Server / Telemetry
      │
      └──────────► Battery Detection
                         ↓
                   Low Battery Event
                         ↓
                       Policy
در این مدل:
•	Provider داده را تأمین می‌کند.
•	Detection شرایط را بررسی می‌کند.
•	Event یک اتفاق را نشان می‌دهد.
•	Policy تصمیم می‌گیرد چه عملیاتی انجام شود.
این مسئولیت‌ها با یکدیگر مخلوط نمی‌شوند.
________________________________________
۲۰. رابطه با Telemetry
Latest Value و Telemetry نیز یک مفهوم نیستند.
Latest Value
برای مصرف داخلی Firmware است.
Battery Latest Value
GPS Latest Value
Signal Latest Value
Telemetry
داده‌ای است که برای ارسال، ثبت یا انتقال به خارج از سیستم آماده می‌شود.
Latest Value
    ↓
Telemetry Creation
    ↓
Telemetry Request
    ↓
Telemetry Queue
بنابراین نگهداری Latest Value الزاماً به معنی ارسال مداوم آن به Server نیست.

۲۱. محدودیت‌های معماری
Providerها نباید:
•	Blocking باشند؛
•	از Delay برای انتظار استفاده کنند؛
•	در انتظار پاسخ سخت‌افزار در حلقه بمانند؛
•	Consumer را برای Acquisition متوقف کنند؛
•	مستقیماً Policy سایر Managementها را کنترل کنند؛
•	Power Manager را مسئول مدیریت جزئیات داخلی خود کنند.
همچنین Consumer نباید:
•	Acquisition زمان‌بر را آغاز کند؛
•	برای دریافت داده منتظر بماند؛
•	جزئیات داخلی Provider را مدیریت کند.

۲۳. اصول تثبیت‌شده
بر اساس تصمیمات معماری، اصول زیر به‌عنوان تصمیمات این بخش در نظر گرفته می‌شوند:
1.	عملیات سریع می‌تواند در محل مصرف انجام شود.
2.	عملیات زمان‌بر باید از مصرف داده جدا شود.
3.	Provider در Super Loop اجرا می‌شود.
4.	Provider خودش Policy مربوط به Acquisition را مدیریت می‌کند.
5.	Provider آخرین داده را آماده نگه می‌دارد.
6.	Latest Value برای مصرف‌کنندگان عمومی و قابل دسترس است.
7.	Consumer مستقیماً Latest Value را مصرف می‌کند.
8.	GetLatest نباید Acquisition جدیدی را آغاز کند.
9.	Latest Value همراه Timestamp نگهداری می‌شود.
10.	تازگی داده از طریق Timestamp قابل تشخیص است.
11.	Provider باید Non-Blocking باشد.
12.	رفتار Provider می‌تواند بر اساس Power Mode تغییر کند.
13.	Power Manager تعیین‌کننده Mode است، نه جزئیات داخلی Provider.
14.	Provider، Request/Queue و Event سه مفهوم متفاوت هستند.
15.	ایجاد Provider مستقل برای همه‌ی داده‌ها الزامی نیست؛ معیار، زمان‌بر بودن Acquisition و نیاز معماری است.
________________________________________
۲۴. جمع‌بندی معماری
در معماری Firmware، داده‌ی مورد نیاز مصرف‌کنندگان نباید در لحظه‌ی مصرف الزاماً تولید شود.
هرگاه تأمین داده زمان‌بر باشد، یک Provider مسئول تأمین آن در پس‌زمینه‌ی منطقی Super Loop خواهد بود. Provider داده را طبق Policy خود به‌روزرسانی کرده و آخرین مقدار را همراه Timestamp نگهداری می‌کند.
مصرف‌کنندگان صرفاً داده‌ی آماده را دریافت می‌کنند.
به این ترتیب:
Slow Acquisition
       ↓

و اصل بنیادی این بخش چنین است:
«داده‌ی زمان‌بر را هنگام نیاز تولید نکن؛ آن را از قبل آماده نگه دار تا مصرف‌کننده فقط مصرف کند.»
